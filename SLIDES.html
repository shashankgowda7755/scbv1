The brief, from the call

  • SCB has a compliance ceiling — personal data must stay inside the Google ecosystem.
  • The Google Form + Sheet workflow is approved, but it has three gaps:
    • No duplicate prevention.
    • No live ops dashboard during the event.
    • No automated retention purge.
  • Ask: close the three gaps without leaving the Google data path.

Quoted concern from Roshney on the meeting recording: "Getting their mobile number is an offence for me. Getting their email ID is an offence for me. Getting their employee ID is an offence."

What we built

1. Operator console

Create events, see live registrations, reveal/mask sensitive data, export CSV, purge.

2. Participant view

One URL per event. QR opens a clean, SCB-branded registration form on the participant's phone.

3. Encrypted storage

Cloud Firestore in Mumbai. Personal fields are ciphertext only. Operator holds the key.

Demo event: CSR Activity Chennai — Quiz Calendar Creation, 09 May 2026, DLF Downtown.

Data flow

1

Operator creates the event in the dashboard. App generates an event-specific URL + QR code.

2

Employee scans the QR on their phone, lands on the participant form.

3

Browser encrypts fullName, employeeId, email, phone with AES-256-GCM. Bank ID is SHA-256 hashed for the document ID.

4

Ciphertext is written to Cloud Firestore. Dashboard updates live via onSnapshot.

5

CSV export decrypts in-browser. Retention TTL or manual purge removes data after the event.

  employeeId:    "enc:v1:<iv>.<ciphertext>",

A database breach hands an attacker ciphertext and IVs. The key never travels with the data.

Field-level encryption — the headline

Algorithm

AES-GCM, 256-bit key, 96-bit IV per record. Authenticated — tampering is detectable. Implemented with the browser's native Web Crypto API. No third-party crypto library.

Key custody

The key is held by the operator. Sourced in this order: REACT_APP_DATA_KEY env var, then localStorage. Never written to Firestore.

Fingerprint

The dashboard shows kid-<6 hex> derived from SHA-256 of the key. Safe to share — identifies the key without revealing it.

Rotation demo

One click generates a new key. Prior records become unreadable. Proves the database is meaningless without the key.

Duplicate prevention without decryption

The duplicate-check value (Bank ID) is hashed with a per-event salt and used as the Firestore document ID.

docId = `${eventId}__${sha256(`${eventId}::${normalize(bankId)}`).slice(0, 24)}`
  • Two submissions with the same Bank ID collide on document ID.
  • Firestore reports "already exists" — we show the Replace dialog.
  • The server never sees the plaintext Bank ID.
  • Different events with the same Bank ID don't collide — the hash is salted with the event ID.

Retention and deletion

Manual purge

Operator clicks Purge Event in the dashboard. The event document and every registration with that eventId are deleted immediately.

Automatic TTL

Every document carries an expiresAt Timestamp. Firestore TTL policy on that field deletes documents within 24 hours of expiry.

SCB does not have to trust us to remember to delete the data. Firestore deletes it.

Firestore security rules (v1)

match /registrations/{id} {
  allow read: if true;
  allow create, update: if
    request.resource.data.eventId is string
    && exists(/databases/$(database)/documents/events/$(request.resource.data.eventId))
    && hasEncryptedShape(request.resource.data.fullName)
    && hasEncryptedShape(request.resource.data.employeeId)
    && hasEncryptedShape(request.resource.data.email)
    && hasEncryptedShape(request.resource.data.phone)
    && request.resource.data.participation in ['Yes', 'No']
    && request.resource.data.photoConsent is bool
    && request.resource.data.dedupeHash is string;
}

Plaintext can't enter the database even from a hostile client. The rule rejects any field that doesn't carry the enc:v1: shape.

Technical challenges we solved

1

"We can't use a non-Google database." Picked Cloud Firestore — same Google account, same vendor surface as a Google Sheet.

2

"We can't hold personal data even by accident." Field-level AES-256-GCM. Ciphertext only in Firestore. Operator holds the key.

3

Duplicate detection without reading PII. SHA-256 hash with a per-event salt as the document ID.

4

Live count without polling. Firestore onSnapshot — sub-second update.

5

Retention SCB doesn't have to babysit. Firestore TTL policy on expiresAt.

One merge away from V2

  • Operator Firebase Auth. Google sign-in + custom claims. Lock dashboard reads/writes to staff only.
  • Audit log. A /audit collection that records every reveal, export, and purge with the operator's UID and timestamp.
  • Google Sheet mirror. A Cloud Function trigger on registration create pushes a decrypted row into an SCB-approved Sheet — keeps the existing handoff format alive.
  • SSO with the bank. Firebase Auth supports SAML/OIDC. Operators log in with their bank credentials.
